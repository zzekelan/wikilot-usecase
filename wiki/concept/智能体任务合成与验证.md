# 智能体任务合成与验证

## 任务不只是一个问题

智能体需要在工具与环境中行动，因此一项训练任务可以表示为：

**任务＝（问题，环境，验证系统）**。

问题说明目标，环境提供代码、文件、API 和依赖，验证系统判断完成程度。三者需一致：描述要求什么、环境允许什么、测试奖励什么，应当互相匹配。来源：[[wiki/source/deepseek-v4-1-flash|报告]]第 25–26 页。

## 质量的两个轴

- **正确性**：任务可执行、测试可靠、描述与验证一致，不泄漏答案。
- **难度**：足够有区分力，同时能产生有用的学习信号。

报告以两者作为构题训练的奖励，并用新一轮 RL 轨迹持续复查旧任务。某任务初次通过质检不代表永远可靠，更强的模型可能发现测试漏洞（第 25–26 页）。

## 两类生产管线

**通用 agent**：根据自愿回传的工作流接口与失败案例，构造 mocked 工具，保持输入输出格式、API schema 和业务约束，生成单轮或多轮环境。

**代码 agent**：选取复杂/失败会话或 GitHub 项目，依次执行：

1. 判断能否容器化运行并自动验证，选任务起点与实现方向。
2. 建依赖、初始工作目录、测试和任务描述，清除答案痕迹，打包镜像层。
3. 多个解题 agent 尝试；独立质检 agent 检查错误、任务–测试错配和投机空间。
4. 修复环境或调整难度，再进入验证。

来源：报告第 26 页。

## 为什么同时需要两类测试

fail-to-pass 测试确认待实现能力从失败变成功；pass-to-pass 测试确认原本正常的功能没有回归。只奖励第一类，可能训练出“修一处、坏多处”的策略。

与[[wiki/concept/正则化方法|数据增强]]相比，这里扩展的是完整交互任务及反馈，而不仅是保持标签的输入变换。它为[[wiki/concept/SFT-RL与OPD|强化学习]]提供可验证奖励，也把[[wiki/concept/泛化与数据质量|数据质量]]扩展到环境和验证器质量。
