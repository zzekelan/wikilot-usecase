# KV 缓存与预填充、解码

## 为什么缓存 Key 和 Value

自回归注意力生成下一个 token 时，需要查询前面各位置的 Key/Value。KV cache 保存这些状态，避免每生成一个 token 都重新计算整个前缀。

- **预填充（prefill）**：处理已知输入序列，建立缓存。输入位置可以批量计算。
- **解码（decode）**：逐 token 生成，使用已有 KV，并将新位置的状态加入缓存。
- **前缀复用（prefix caching）**：后续请求共享某段输入时，直接复用该前缀已算出的状态。

智能体反复调用工具、读入工具输出，会产生大量新输入和可复用前缀，因此 prefill 与缓存搬运都可能成为成本中心。来源：[[wiki/source/deepseek-v4-1-flash|DeepSeek 报告]]第 4–6、9 页。

## 三种缓存口径

| 缓存 | 覆盖范围 | 主要成本 |
| --- | --- | --- |
| 全局 KV | 可跨越整个上下文；报告含 main KV 与 indexer K | 长序列下 HBM 容量与读取 |
| 局部 SWA KV | 最近固定窗口 | 每层局部状态，随窗口而非总序列增长 |
| 持久 KV | 跨请求保存以复用前缀 | SSD/主机内存、迁移带宽、保留时间 |

同一全局状态可能同时有运行时与持久副本；“全局”和“持久”不是互斥分类。来源：报告第 4、19–20 页。

## 缩小缓存的四个方向

可从每条目大小、序列压缩、跨层共享和数值位宽着手。常规多头缓存可粗略写为 N×L×2×n_KV×d_head×每元素字节数；共享 latent、稀疏压缩等结构会改变这个计数，需按实际布局核算。

报告将全局缓存降为 **890 B/token**。按 1,000,000 token 估算约 890 MB（十进制），这里只算全局 KV；完整部署还包括模型权重、SWA、激活等。持久缓存另外通过不长期存 SWA 节省容量（第 1、19、37 页）。

衡量系统效率时，应同时看缓存命中率、输入长度、首 token 延迟、输出速度与并发吞吐；“少一半缓存”与“快一倍推理”涉及不同瓶颈。
